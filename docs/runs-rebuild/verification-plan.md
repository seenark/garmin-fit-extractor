# แผนตรวจสอบ Runs rebuild

สถานะ: **ข้อเสนอเพื่อขออนุมัติ** ยังไม่ได้ทำ Runs rebuild และยังไม่ได้รัน acceptance tests ของระบบใหม่ เอกสารนี้กำหนดสิ่งที่จะต้องพิสูจน์หลังอนุมัติ ไม่ใช่รายงานว่าฟีเจอร์ผ่านแล้ว ไม่ให้สิทธิ์ reset, migration หรือ deploy ระบบจริง

ข้อกำหนด D01–D24 เป็นข้อกำหนดที่ล็อกไว้ ดู [architecture](architecture.md), [implementation plan](implementation-plan.md), [decoder assessment](decoder-assessment.md) และ [LT method assessment](lt-method-assessment.md) สำหรับสถาปัตยกรรม ลำดับงาน และประตูตัดสินใจที่เกี่ยวข้อง ข้อเสนอหลักคือเก็บ original FIT แบบ immutable ใน PostgreSQL `BYTEA`, ใช้ durable PostgreSQL queue และเผยแพร่ revision ที่ครบชุดแบบ atomic ไม่เก็บ original ZIP และไม่เพิ่มที่เก็บ FIT แบบ public/static

## 1. แยกสถานะและประเภทหลักฐาน

- **ตรวจแล้วในระบบเดิม:** baseline จาก checkout ที่แยกจากงานเขียนเอกสาร ตามหัวข้อ 2 เท่านั้น ไม่ใช้ผลนี้รับรอง AT ของ rebuild
- **ยังไม่รัน:** AT-01–AT-36 ทุกกรณีในตารางด้านล่าง ไม่มีเครื่องหมายผ่านโดยอนุมานจากโค้ดหรือ unit tests เดิม
- **ทดลอง:** decoder corpus และการศึกษาวิธี LT เป็น feasibility evidence ไม่ใช่ความครบถ้วนของ importer, export หรือความถูกต้องทางสรีรวิทยา
- **ถูกกั้นด้วยหลักฐาน:** full decoded schema ต้องผ่าน decoder fidelity gate; numerical LT1 และ LT2 ต้องผ่าน primary-method gate และ reference validation ของแต่ละเป้าหมาย การส่งคืน `null` ทุกครั้งไม่ทำให้ P4 เสร็จ
- **นอกขอบเขตรอบนี้:** implementation, production reset/migration/deploy, การอ่าน secrets หรือ FIT ส่วนตัว และการเรียก LLM/API เพื่อประมวลผลหรือเป็นผู้ตัดสิน

แยกการตรวจสามชั้นเสมอ: (1) extraction/software correctness เทียบ bytes, FIT specification และ golden data; (2) workload-pattern detection เทียบ annotation ที่ไม่อ้างเจตนาของผู้วิ่ง; (3) physiological validity เทียบ reference ที่ตรงกับ LT target วิธีที่ผ่านชั้นแรกไม่ได้ผ่านชั้นที่สามโดยอัตโนมัติ

## 2. Baseline ที่สังเกตแล้วและวิธีทำซ้ำอย่างปลอดภัย

Baseline ที่รายงานจาก fresh `git archive` ของ HEAD `d90051ce2cb398678a7c16b6b981724673e8028f` ใช้ frozen Bun install และ PostgreSQL 18 แบบชั่วคราว ไม่ใช้ฐานข้อมูลเดิม:

| คำสั่ง/พื้นผิวเดิม | ผลที่สังเกต | ความหมายและข้อจำกัด |
| --- | --- | --- |
| `bun run check` | exit 0 | ตรวจระบบเดิม ไม่ใช่ rebuild |
| `bun run test` | exit 0; web 95, CLI 8, Rust 71 ผ่าน | ไม่รับรอง end-to-end workflow หรือความถูกต้องของ LT |
| `bun run build` | exit 0 | build ของระบบเดิม |
| `bun run test:e2e` | exit 1; ผ่าน 3, ไม่ผ่าน 1 | `apps/web/e2e/extractions.spec.ts:210` คาด URL `order=asc` แต่ได้ `order=desc`; end-to-end workflow ยังไม่ผ่านทั้งหมด ไม่ได้ระบุ root cause และไม่ได้แก้หรือรันซ้ำเพื่อยืนยัน |
| Rust `fit_decode` tests เดิม | อยู่ใน Rust suite ที่ผ่าน | มี default CRC validation และการปฏิเสธ corrupt FIT แม้ wrapper ไม่มีฟังก์ชัน CRC แยก ผลนี้ไม่พิสูจน์ fidelity ทุก field |
| Numeric LT / deployment budgets | ไม่ได้ตรวจ | ไม่มีผล benchmark หรือ physiological validation ให้ใช้รับรอง |

คำสั่งต่อไปนี้เป็นวิธีทำซ้ำในอนาคต ไม่ได้รันเพิ่มโดยผู้เขียนเอกสาร ต้องใช้สำเนา repository ที่ไม่มี `.env`/secrets และ shell สำหรับการทดสอบเท่านั้น ต้องมี Bun 1.3.14, Rust/Cargo และ PostgreSQL 18 client/server tools ใน `PATH`; พอร์ต 55432, 3000 และ 5173 ต้องว่าง หาก start database ไม่สำเร็จ ให้หยุด ไม่ fallback ไปหา database อื่น

**คำเตือน:** `apps/api/tests/http.rs` มี `TRUNCATE ... RESTART IDENTITY CASCADE` ที่รวมตารางผู้ใช้และ auth ห้ามตั้ง `TEST_DATABASE_URL` หรือ `DATABASE_URL` ของชุดทดสอบนี้ให้ชี้ฐานข้อมูลที่มีอยู่แล้ว แม้จะเป็น development database ห้ามคัดลอก SQL ของ test helper ไปเป็น Runs reset

```sh
# รันจาก fresh archive/สำเนาที่ไม่มี .env; ใช้ shell ใหม่สำหรับงานนี้
set -eu
unset DATABASE_URL TEST_DATABASE_URL PGHOST PGDATABASE PGUSER PGPASSWORD
VERIFY_ROOT="$(mktemp -d /tmp/runs-verify.XXXXXX)"
export PGPORT=55432
initdb -D "$VERIFY_ROOT/pgdata" -U runs_verify -A trust --no-locale
pg_ctl -D "$VERIFY_ROOT/pgdata" -l "$VERIFY_ROOT/postgres.log" \
  -o "-h 127.0.0.1 -p $PGPORT -k $VERIFY_ROOT" -w start
trap 'pg_ctl -D "$VERIFY_ROOT/pgdata" -m fast -w stop' EXIT
createdb -h 127.0.0.1 -p "$PGPORT" -U runs_verify runs_verify
export TEST_DATABASE_URL="postgresql://runs_verify@127.0.0.1:$PGPORT/runs_verify"
export DATABASE_URL="$TEST_DATABASE_URL"
psql "$TEST_DATABASE_URL" -X -v ON_ERROR_STOP=1 \
  -c 'SELECT current_database(), current_user, inet_server_port();' \
  -c 'SHOW server_version;' -c 'SHOW data_directory;'
test "$(psql "$TEST_DATABASE_URL" -X -Atc 'SHOW data_directory;')" = "$VERIFY_ROOT/pgdata"
test "$(psql "$TEST_DATABASE_URL" -X -Atc 'SHOW server_version_num;')" -ge 180000
test "$(psql "$TEST_DATABASE_URL" -X -Atc 'SHOW server_version_num;')" -lt 190000
bun install --frozen-lockfile
bun run check
bun run test
bun run build
bun run test:e2e
```

ตรวจ output ของ `data_directory` ว่าอยู่ใต้ `VERIFY_ROOT` และชื่อ database/user/port ตรงกับที่สร้างก่อนรัน suite เก็บ exit codes และ logs แยกแต่ละคำสั่ง หากคำสั่งใดไม่ผ่าน shell จะหยุดและ shutdown cluster ไม่แก้ expected result ให้ตรงกับ output เพียงเพื่อทำให้ผ่าน `scripts/e2e.ts` ใช้ `TEST_DATABASE_URL` ก่อน `DATABASE_URL`, เปิด API/Vite และติดตั้ง Chromium; test-auth ที่ script เปิดต้องจำกัดอยู่ในสภาพแวดล้อมชั่วคราวนี้ สูตรนี้ไม่ใช่ production runbook และไม่อ้างว่าเครื่อง workstation เท่ากับ deployment target

## 3. Fixture, oracle และการตรึงเงื่อนไขก่อนตรวจ

### 3.1 แหล่งข้อมูลและสิทธิ์

1. ใช้ `apps/api/tests/fixtures/activity.fit` ที่ README ระบุว่ามาจาก `fitparser` MIT fixture `tests/fixtures/Activity.fit` พร้อม `activity.zip` สำหรับ archive integration เก็บ attribution/license และ upstream revision ใน manifest ตัว FIT ที่ตรวจในรอบนี้มีขนาด 771 bytes, SHA-256 `90bf03369eb0bf70275d3c2d3f9496d2b6fea54edd6ed03be271eb02b4e9ab93`
2. ใช้ synthetic corpus ที่ decoder spike สร้างและอธิบายใน [decoder assessment](decoder-assessment.md): `/tmp/runs-decoder-spike-20261004/corpus`, generator `generate.py` แบบ CC0-1.0 และ provenance/license/hash ใน `manifest.json` ของ directory งานทดลองเดียวกัน ส่วน `public_activity.fit` เป็น MIT fixture ที่ byte-identical กับ fixture repository ข้างต้น จำนวน/ผลสุดท้ายให้ยึด decoder assessment ไม่ถือ path ชั่วคราวเป็น fixture ที่ durable ใน repository การรับ implementation ต้องมี generator, seed/options, manifest, hash และคำสั่งสร้างซ้ำที่ถาวรตาม gate
3. Fixture ใหม่ทุกตัวต้องมี source URL/revision หรือ generator revision, license/permission, hash, ขนาด, feature ที่ตั้งใจทดสอบ, expected output และที่มาของ oracle ZIP manifest ต้องระบุ hash ของสมาชิก FIT ไม่ใช่เฉพาะ hash ของ container
4. ห้าม commit FIT ส่วนตัวหรือ raw identifiers/location จากผู้ใช้ลง repository ข้อมูล reference ของมนุษย์ที่มี permission ต้องอยู่ในที่เก็บจำกัดสิทธิ์และมี pseudonymous manifest แยกจาก public fixtures หาก license ไม่อนุญาตแจกจ่าย ให้กำหนดการเข้าถึงที่ตรวจสอบได้ ไม่คัดลอกข้อมูลโดยพลการ
5. ใช้ corpus เดียวกันกับ versions/options ที่ pin ใน decoder assessment: Rust `fitparser` 0.11.0 (profile 21.202.0), Python `fitdecode` 0.11.0 (profile 21.171.0), official Python `garmin-fit-sdk` 21.217.0 และ JavaScript SDK 21.208.0 หากใช้ตรวจ compatibility เดิม เปรียบเทียบ source identities, fields, order, raw/expanded values, warnings และ failure modes ความเห็นตรงกันไม่ใช่ oracle หากขัดกันต้องตรวจ specification/encoding ของ generator; unsupported capability ต้องปรากฏใน coverage matrix ไม่อ้าง fidelity 100% **การรัน comparative probe เพิ่ม การ benchmark และการเผยแพร่ที่เกี่ยวกับ official SDK ต้องผ่าน license review ก่อน** เนื่องจาก decoder assessment พบข้อจำกัด §2(f) ใน `@garmin/fitsdk` license ไม่ให้สูตรรันซ้ำแบบไม่มีเงื่อนไข และไม่ใช้ diagnostics เดิมจัดอันดับความเร็ว
6. Synthetic fixtures พิสูจน์ arithmetic, boundary และ state transition ของวิธี LT ได้ แต่ไม่พิสูจน์ว่า LT ตรงกับสรีรวิทยาของคน และไม่แทน reference dataset
7. ข้อค้นพบจาก source/error/capability probes เป็น observations ไม่ใช่ permission ให้รันหรือเผยแพร่ comparative benchmarks ห้ามเผยแพร่ timing/memory comparative benchmarks ของ official SDK ก่อน legal gate §2(f) ผ่าน การวัด deployment budgets ให้ใช้ implementation ที่มีสิทธิ์ตรวจและ target environment ที่กำหนด ไม่ใช้ official SDK ranking

Decoder assessment พบ blocker ใน Rust `fitparser` 0.11.0 สำหรับ packed component bounds/accumulation: valid 3-byte HR payload ที่มี 2 events ถูกขยายเป็น 10 elements รวม synthetic zeros และไม่ใช้ preceding anchor ผล negative probe นี้ไม่ใช่ rebuild acceptance ที่ผ่าน ต้องแก้ general component expansion แล้วผ่าน AT-06 และ corpus เดิมก่อนประกาศ full fidelity ไม่แก้ด้วยการกรอง zeros เพราะ zero ที่ถูกต้องยังต้องรักษา

### 3.2 Oracle และการเปรียบเทียบ

- Decoder goldens ผูกกับ numeric message/field identity, developer identity และ encoding ตาม FIT profile/specification ไม่ใช้ชื่อ UI เป็น oracle ต้องระบุ field ที่ decoder ไม่รองรับกับ warning อย่างชัดเจน
- Normalization goldens แยก elapsed/timer/moving time, UTC/source offset, units, recorded/calculated และ source precedence ตัวเลขต้องมาจาก fixture ที่ทราบ encoding ไม่มาจากผลของ implementation ที่กำลังตรวจ
- Clock, version, configuration, input hashes และ reference manifest ต้องตรึงเพื่อเปรียบเทียบ payload ที่ทำซ้ำได้ เปรียบเทียบ JSON เชิงความหมายสำหรับคนละ snapshot; Copy/Download ที่ใช้ snapshot เดียวกันต้องได้ pretty JSON bytes เดียวกันรวม newline/metadata
- Privacy oracle เป็น canary corpus ที่มี location/identifier หลาย representation และหลายระดับ nested ตรวจ decoded/normalized/derived รวม unknown/developer ทั้งสองโหมด ตรวจด้วย schema classification และ recursive token/value search ไม่ใช้การหา key ชื่อ `latitude` เพียงอย่างเดียว Omission manifest ต้องไม่มีค่าที่ซ่อน ชื่อไฟล์ส่วนตัว หรือ identifier ที่สร้างกลับได้
- งาน crash/delete/race ต้องใช้ synchronization barriers และ failpoints ที่กำหนดตำแหน่งแน่นอน ไม่ใช้ sleeps ที่หวังให้ race เกิด ต้องตรวจทั้ง public API, database publish manifest และ worker ที่กลับมาทำงาน ไม่ตรวจเฉพาะข้อความสำเร็จ

## 5. Workload detector: annotation และ acceptance ก่อนเปิดผล

P3 ต้องกำหนด annotation protocol และ candidate policy ก่อน evaluation: ชนิด steady/interval/recovery/strides, boundary/gap rules, minimum usable duration, artifact flags, ambiguity/unknown และ eligibility โดยไม่อิงชื่อ workout หรือผล LT ให้ผู้เชี่ยวชาญสองคน annotate อย่างอิสระจาก FIT evidence ที่อนุญาต และ adjudicate ข้อขัดแย้งโดยบันทึก original annotations รายงาน inter-rater agreement และเหตุผลที่ตัวอย่าง ambiguous ไม่ถูกให้ label แน่นอน

แบ่ง development กับ validation ด้วย person/activity/observation-group ก่อน tune parameters ทุก repetition/window ของคนและกิจกรรมที่สัมพันธ์กันอยู่ฝั่งเดียวกัน ห้ามใช้ validation labels เลือก threshold หรือแก้ candidate policy หลังเห็นผล งาน calibration ของคนหนึ่งต้องใช้เฉพาะช่วงเวลาที่อยู่ก่อน evaluation cutoff ของคนนั้น ไม่ใช้ future history

**ข้อเสนอ engineering gate ที่ยังไม่อนุมัติ:** สำหรับ workload classes ที่ปล่อยใช้งาน ให้ one-to-one temporal matching ด้วย intersection-over-union >=0.5 โดยไม่จับคู่ข้าม timer pause; precision ต่อ class >=0.90 และ recall ต่อ class >=0.80 บน independent validation activities รายงาน confusion matrix, false positive/negative, boundary error, per-class support และ activity/person-clustered uncertainty พร้อม macro และ per-class scores ตัวเลขนี้เป็น proposed product gate ของ workload pattern ไม่ใช่ physiological threshold หรือผลที่วัดแล้ว ต้องยืนยัน population, annotation rules, sample-size/uncertainty plan และ acceptance version ใน P1 ก่อนเปิด validation หาก class ไม่มี support เพียงพอให้สถานะ evidence insufficient ไม่ตัด class นั้นออกจากคะแนนเงียบ ๆ

อย่านับ 20 overlapping windows เป็น 20 independent successes อย่าเพิ่ม precision ด้วยการ abstain ทุก case: รายงาน eligibility/coverage/abstention และเหตุผลพร้อม detector scores หากต้องเปลี่ยน gate หลังตรวจ ให้ทำ amendment ล่วงหน้า ใช้ validation set ใหม่ และแสดงผลเก่า ไม่ตั้ง budget ย้อนหลังให้พอดีกับ output

## 6. Numerical LT: method-specific gate ไม่ใช่ regression test อย่างเดียว

ใช้ [LT method assessment](lt-method-assessment.md) โดยเฉพาะ G1–G5 เป็นแหล่งตัดสินวิธี ข้อเสนอ candidate คือ DFA-a1 0.75/0.50 สำหรับ running VT1/VT2 proxies จาก exercise beat-to-beat RR ไม่ใช่ direct blood-lactate LT1/LT2 การใช้ slot LT1/LT2 ต้องรักษา `targetDefinition` และคำว่า proxy ข้างค่า ไม่สลับชื่อ target เงียบ ๆ แต่ละ target ต้องมีเอกสาร reference construct, protocol, sport/population, required inputs และ assumptions ที่ FIT ตรวจไม่ได้ Device-recorded lactate threshold เป็น recorded setting/metric ไม่ใช่ independent lab reference

ดู [proposed threshold-method ADR](../adr/0005-runs-threshold-methods.md) ประกอบ ข้อเสนอยังไม่ได้รับอนุมัติ การทดลอง LT ที่สังเกตจริงในรอบนี้มีเพียง arithmetic crossing และการคำนวณ errors ซ้ำจาก published table ตาม LT assessment ยังไม่ได้รัน DFA algorithm, FIT→RR→LT engine หรือ physiological validation จึงไม่เปลี่ยนสถานะ AT-17 หรือ numerical gates เป็นผ่าน

### 6.1 Gate ก่อน implementation/release

1. **Primary-method assessment:** ตรวจ reproducibility ของ formula/algorithm, protocol eligibility และความแตกต่างระหว่าง correlation กับ individual agreement/error ไม่ใช้ drift 5%, arbitrary fastest 30 minutes, fixed LT1/LT2 ratio หรือ HRmax/zone mapping แทนหลักฐาน
2. **Software method fixtures:** AT-17 ต้องมี numerical positive case และ noisy/negative/conflict cases ที่คำนวณ oracle อย่างอิสระ Trace ต้องออกจาก engine จริง ไม่ให้ LLM judge และไม่ใช้ synthetic data รับรอง physiology
3. **Reference dataset:** ต้องมี permitted running dataset ที่มี paired raw exercise RR และ independently assessed gas-exchange VT1/VT2 สำหรับ candidates นี้ พร้อม measurement uncertainty, timing, preprocessing, exclusions และ protocol deviations ตาม LT assessment ยังไม่ยืนยัน corpus ที่มี reuse permission และ raw input ครบ OSF SRVHC แสดง `Dataset.xlsx` แต่ metadata เป็น No license และยังไม่ได้ตรวจ cells; S1/S2/S5 ระบุ raw data on request ไม่ใช่ permission ให้ใช้หรือ redistribute ให้แสดง gate blocked พร้อม prerequisite ที่ขาด ไม่ส่ง null-only estimator แล้วทำเครื่องหมาย P4 complete และไม่ลบ P4 จากแผน หากต้องการ lactate claim ต้องมี paired running lactate reference เพิ่มตาม exact definition
4. **Pre-registration:** ตรึง method/config/version, units, target matching, numerical tolerance, error/bias/agreement screens, coverage และ uncertainty ก่อนเปิด validation ใช้ G1 tolerance 1e−9 เฉพาะ same mathematical configuration; ไม่เทียบ arbitrary preprocessing/Kubios version ด้วย tolerance นี้ G4 เสนอ published-replication research screens สำหรับ VT1 HR: absolute bias <=1.9 bpm และ LOA ภายใน ±12.2 bpm; VT2 HR: absolute bias <=4 bpm และ LOA ภายใน ±24 bpm โดยตรวจ clustered confidence bounds ด้วย ตัวเลขเหล่านี้ไม่ใช่ medically acceptable budgets หรือ validated release และยังไม่ได้วัดกับระบบนี้ G5 เสนอ paired MAE/LOA width ไม่แย่กว่า independent reference-repeat ของ protocol/population เดียวกัน โดย upper confidence bounds ของ excess ไม่เกินศูนย์ Sample size, eligible coverage และ reference-repeat limits ยัง blocked จนมี corpus/variance ต้องกำหนดจาก development และอนุมัติก่อน holdout ไม่ตั้งย้อนหลังให้ผ่าน
5. **Independent validation:** แยกคนเป็นหลักและกัน activities/recurrences/overlapping windows/duplicate observations ข้าม development/calibration/validation ผู้ที่มี repeated measures ต้องประเมิน clustered uncertainty และรายงาน within-person/between-person แยก ใช้ event-time cutoff ทั้งเลือก evidence และ calibration จับคู่ reference ด้วย tolerance ที่ตรึงไว้ ไม่มี future leakage หรือ reference ของ person อื่น DFA centered 120-s window ต้องมีข้อมูลเต็ม t−60 ถึง t+60 ก่อน cutoff ห้ามเติม beats จาก next activity หรืออ้างว่า window center ก่อน cutoff เพียงอย่างเดียวเพียงพอ

### 6.2 ผลที่ต้องรายงานต่อ target และต่อวิธี

รายงานจำนวนคน/กิจกรรม/effective independent observations, eligible coverage, numerical-output coverage, abstention/low-confidence พร้อม reasons และแยก sensor availability/protocol/population รายงาน signed bias, MAE/RMSE หรือ robust error ที่ pre-register, error distribution และ agreement limits ที่เหมาะกับ repeated measures; correlation เพียงอย่างเดียวไม่พอ รายงานความผิดพลาดในหน่วย physiological target และการแปลงเป็น HR/pace/power แยก ไม่ถือผลดีในหน่วยหนึ่งรับรองอีกหน่วยหนึ่ง

Uncertainty interval ต้องมีนิยามจริงและ coverage/error-width ตรวจบน independent reference หากรายงานเพียง heuristic confidence score ต้องเรียกตามจริง ไม่อ้าง 95% CI ตรวจ uncertainty/abstention calibration และ false confident outputs ไม่ให้ตัวเลขเฉลี่ยที่ดูดีซ่อนข้อผิดพลาดกลุ่มใหญ่ เมื่อวิธีขัดกันต้องรายงาน conflict โดยไม่ clamp เพื่อให้ LT1 < LT2 หรือให้ตรง device metric

P4 ต้องมี real numerical engine พร้อม positive FIT→RR→analysis path, software/trace/history/suggestions gates และ gates ของ intended release ไม่ใช่ null-only placeholder Experimental proxy ที่ผ่าน G1/G2 ต้องติด experimental/target/limits และไม่ถือว่าผ่าน G5; validated claim ต้องผ่าน G5 และ lactate claim ต้องมี lactate-specific running evidence ส่วน unsupported input cases abstain ได้อย่างมีเหตุผล หาก research gate ยังไม่ผ่าน core import/export ส่งได้ตาม P2 แต่ LT แสดง not released/researchBlocked ชัดเจน ไม่อ้างว่าข้อกำหนด numerical LT เสร็จแล้ว

## 8. Protected boundaries และการเก็บหลักฐานรับงาน

Reset/release rehearsal ต้องใช้ disposable database เท่านั้น Protected tables คือ `users`, `sessions`, `oauth_states`, `oauth_login_requests`, `oauth_authorization_codes`, `oauth_access_tokens`, `oauth_refresh_tokens`, `transcript_entries`, `legacy_imports` ตาราง Runs เดิมคือ `extractions` และ `activities` ไม่ใช่ `activity_rows`; `activities.id` อ้าง `extractions` และ owner อ้าง `users` พร้อม cascade ดังนั้นการลบ users อาจลบ Runs และ auth ตามมาได้ แต่ไม่ใช่วิธี reset Runs ต้องไม่ลบ users เลย Shoes เป็น checked-in catalog/frontend surface ที่ต้องตรวจแยกจาก database counts

หลัง implementation เก็บ evidence ต่อ AT: command/run ID, commit/config/version manifest, fixture hashes, exact assertions, observed output และ status `passed`/`failed`/`blocked`/`not run` ตามจริง พร้อมภาพ surface เมื่อเป็น UI และ checksum/row assertions เมื่อเป็นข้อมูล ห้ามบันทึก private FIT values, account email, device IDs, token หรือ location ลง logs/report แม้ test เป็นเรื่อง privacy
